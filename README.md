# novel-engine

Canon 驱动的中文长篇小说引擎。一句话概括：**把"故事状态"从 prompt 里拿出来，变成可查询、可版本化的结构化 Canon；每章只喂"这一步需要的事实"。**

命令行工具，自带状态与校验。默认接 DeepSeek，也能离线用 mock 跑通全流程；千章规模验证过数据层不退化。

## 它解决什么

| 长篇写作的真实问题 | 这个引擎的做法 |
|---|---|
| 写到 200 章，第 10 章埋的伏笔丢了 | 伏笔有到期章、回声记录、死笔预警，到期强制进上下文 |
| 角色说出他还不该知道的事 | 信息差：谁已经知道、读者知道多少，分开记 |
| 每章都在解决同一个小麻烦 | 弧级预演：先定整弧的代价递进和转折 |
| 早期细节找不回来 | 长程召回：按人物/物名/词面打分，成稿才算前情 |
| 上下文越写越长直到爆掉 | token 预算 + 按违规代价逐级降级 |
| 写歪了整章重来、钱白花 | 写前约束（禁止发生 / 停笔点）+ 断点恢复 |
| 不知道花了多少钱 | 全任务 token/耗时账本 |
| 一千章要守着点 | `novel batch` 批量推进，失败可续 |

## 安装（Windows）

```powershell
git clone https://github.com/hsjshzbs4-ctrl/novel.git
cd novel
```

然后**双击 `scripts\install.cmd`**，或：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install.ps1
```

脚本优先用 `pipx` 装成全局 `novel` 命令；没有 pipx 就在项目里建 `.venv`。

需要 Python 3.10+（安装时勾选 Add to PATH）。配置 Key、常见故障见 [docs/install.md](docs/install.md)。

> 目前只支持 Windows；macOS / Linux 未验证，不做承诺。

## 配置

复制 `.env.example` 为 `.env`：

```bash
# 离线跑通全流程（默认）
NOVEL_PROVIDER=mock

# 接 DeepSeek
NOVEL_PROVIDER=deepseek
DEEPSEEK_API_KEY=sk-...
DEEPSEEK_BASE_URL=https://api.deepseek.com
```

按任务覆盖模型（可选）：

```bash
NOVEL_MODEL_WRITER=deepseek-flash     # 正文
NOVEL_MODEL_ARCHITECT=deepseek-v4-pro # 架构/规划可以换更强的模型
```

> **模型名以 `GET /models` 为准，不要凭印象填。** 本项目实测时该接口只返回
> `deepseek-flash` 和 `deepseek-v4-pro`，写 `deepseek-v4.1-flash` 这类名字会直接 400。
> 查法：`curl https://api.deepseek.com/models -H "Authorization: Bearer $DEEPSEEK_API_KEY"`

## 用法

```bash
novel init "断碑" --genre 玄幻 --chapters 120 --words 3000
novel architect --idea "被逐出师门的少年，靠残缺传承重登仙途"
novel rehearse --arc 1          # 先定整弧事件骨架
novel plan --count 10           # 章纲逐条落实预演事件
novel write --ch 1
novel batch --from 1 --to 20    # 批量推进，适合挂夜里
novel export --format docx      # 装订成书
novel status
novel doctor
```

产出：

```
断碑/
├── novel.db          # Canon + 版本历史 + token 用量
├── chapters/ch-001.md
└── outline/
    ├── book.md       # 角色、规则、弧
    └── chapters.md   # 章纲
```

## 实测（deepseek-flash）

真实联调，24 章项目、单章目标 900 字：

| 步骤 | 耗时 | 产出 |
|---|---|---|
| `architect` | 11.4s | 5 角色 / 5 规则 / 4 地点 / 3 弧 |
| `rehearse --arc 1` | 20.8s | 10 章事件骨架，代价逐级升高，弧末落在转折点 |
| `plan --count 3` | 5.8s | 3 章章纲，逐条落实预演事件 |
| `write --ch 1` | 20.8s | **863 字**，校验通过，上下文 1,237 / 6,000 tokens |

`deepseek-flash` 支持 JSON 模式、`temperature` 和 usage 统计，适合默认使用。

## 架构

```
Canon（唯一事实来源）
  ├── characters   人物卡（状态、目标、死亡章节）
  ├── rules        不可违背的世界规则
  ├── foreshadows  伏笔账本（埋下 / 到期 / 回收）
  ├── timeline     已发生事件
  ├── arcs/chapters 弧 → 章纲 → 成稿状态
  └── rehearsal_events 弧预演事件（planned → committed）

pipeline/
  architect  创意 → 角色 + 规则 + 弧
  rehearse   弧 → 事件骨架（先定代价递进，再写章纲）
  planner    弧 + 预演事件 → 章纲（含钩子、伏笔动作）
  writer     章纲 → 正文 → 确定性校验 → 压缩摘要 → 回写 Canon
```

### 弧级预演

逐章即兴生成的通病是"每章都在解决同一个小麻烦"。所以写章纲前先把整条弧推演成事件骨架：

```
谢无咎挑炭进外门 → 试探石龛右臂渗血 → 苏窈替他偷钥匙被杖责废手
→ 老哑暴亡 → 冬至禁灵硬撬龛锁灵力逆流 → 翻到第十行，刮痕下是自己的名字
```

**状态语义是这个设计的核心**：预演产出的是 `planned`（计划），不是事实。只有对应章节成稿、且预演点名的参与者确实出场，才转成 `committed`；下一轮预演只读 `committed`，避免计划污染历史。

`novel status` 里的「弧预演 1 已兑现 / 9 待兑现」就是这个账本。

### 分层规划

L0 Canon → L1 全书（角色/规则/弧）→ L2 章纲 → L3 正文。

每层只消费上一层，**不允许跨层**：正文阶段读不到"全书大纲"，只能读本章章纲 + 相关人物卡。这是防 OOC 的核心。

### 长线伏笔

第 10 章埋、第 150 章收的伏笔，靠三个字段活着：

| 字段 | 作用 |
|---|---|
| `due_chapter` | 计划回收章。没有它就只能等"逾期"才发现，那时已经晚了 |
| `planted_context` | 埋下时的处境（目标 + 场景）。回收时只有一句抽象描述是接不上的 |
| `last_echo_chapter` | 最近一次被提及的章。用来发现"埋了就再没出现过"的死笔 |

每章写作前，未回收伏笔按紧迫度分三档，前两档会强制进入上下文：

```
已到期        → 本章必须回收
临近回收      → 还差 10 章以内，本章该让读者重新想起它
长期没有回声  → 沉默超过 60 章，建议至少提一句，别让它变成死笔
```

这三档放在【到期伏笔】里，**预算降级不会丢掉它们**（其他伏笔会被逐条裁掉，这一栏只去掉语境描述）。章纲阶段会检查：到期章必须安排 `payoff` 或 `echo`，否则告警。

回收后伏笔才真正关账（`status=resolved`）。不关账的话账本只增不减，几百章之后每次写作都要在一堆已回收的旧伏笔里挑。

> 实测：24 章的项目里，模型主动把新伏笔的回收章排到了第 62、74、90 章——它确实会做长线规划。超出全书计划章数的会告警（那种伏笔按现有规划永远收不回来）。

### 信息差与写前约束

**信息差**是「作者真相」和「角色认知」的分界：同一个真相，作者知道、部分角色知道、读者可能还不知道。写作时把它显式喂给模型，它才不会让角色说漏嘴。

```
信息差:
  - 十二年前那场大火是沈鹤龄授意点的…
    还不知道的人：['谢无咎', '柳青梧', '苏问梅']  读者已被告知：False
```

- `known_by` 记录谁知道；`revealed_chapter` 记录读者何时被告知；
- 写章时只放「本章出场角色里还有人不知道」的条目，全员已知的自动过滤；
- 部分人知道、部分人不知道的排前面——那是最容易说漏嘴的情形。

**写前约束**是章纲里的两个硬字段：

| 字段 | 作用 |
|---|---|
| `must_not` | 本章**禁止发生**的事（谁不能知道什么、谁不能死、哪条线不能推进） |
| `stop_at` | 停笔点：本章写到哪一幕为止 |

实测一章的约束：

```
禁止发生：谢无咎不得踏上山门石阶的任何一级；沈鹤龄不得离开祖师殿，不得与谢无咎照面
停笔点：停在谢无咎蹲在阶下扒开窑灰，从灰里捻出一粒没烧透的砖渣——断面还是新的
```

生成结果：正文里"踏上/走上/迈上"出现 **0 次**，沈鹤龄全程在殿内下令，结尾正好停在砖渣那句。Critic 也会拿这两条当硬指标，写在禁词前面检查。

### 确定性校验

`novel write` 后会跑一批零成本检查（不花 token、不产生幻觉）：

- 已死亡角色是否在后续章节正常出场
- 章纲引用的角色是否存在
- 伏笔是否超期未回收
- 正文字数是否低于目标的 60%

有 `error` 的章节标记为 `rejected`，改完重跑 `write` 覆盖即可。

### 长程召回

写到第 200 章时，"这个配角上次出场是什么时候""那块玉佩是哪章拿到的"——最近 3 章摘要是答不了的。

做法是**不做语义检索**。连载要维护一致性时，要召回的线索几乎总是人名、物件名、地点名，所以按四样东西打分：

| 信号 | 权重 | 说明 |
|---|---|---|
| 出场角色重合 | 4 / 人 | 章纲里点名的人 |
| 人名出现在正文 | 3 / 人 | 名字被提到但没进章纲 |
| 查询词子串命中 | 3 / 词 | "玉佩"这类物件名 |
| 字符二元组重合 | 0.5 / 个（上限 10） | 兜住模糊表达 |
| 近因 | 1 / (1 + 章龄/40) | 同等相关时偏向近期 |

**只有成稿的章节才算"前情"**——规划中的章节是计划，不能冒充已发生的事实。这条是踩出来的：第一版把还没写的第 6 章当成"前情"召回了，分数还最高。

写作时自动注入 top-4 到【相关前情】，并排除最近 3 章（它们已经在【前情摘要】里）。也可以手动查：

```bash
$ novel recall "云蘅"
章  标题      分数   摘要
3   西山界碑  11.4   云蘅派石决明重立西山塌碑…
1   山门碑下  11.3   石决明以刻碑匠身份入青云宗画押，云蘅定下每月查验…
```

纯 Python，500 章规模下一次检索是几千次字符串比较，微秒级。不需要索引表，也不需要向量库。

### 上下文预算

`novel write` 的上下文按 token 预算裁剪，默认 6000（`NOVEL_CONTEXT_BUDGET` 可改）。

做法不是"字数 × 系数"估算，而是先构建完整 payload、**实测序列化长度**，超预算再按固定顺序逐条降级：

```
文风压缩 → 伏笔逐条 → 前情摘要逐条 → 世界规则逐条 → 场景压缩 → 角色卡瘦身
```

顺序按"违规代价"排：伏笔总账排在最前，因为**本章要回收的伏笔已经写在章纲里了**，整本总账对单章写作的价值低于刚发生的前情；世界规则是硬约束，留到最后。

章纲和出场角色是硬需求，任何预算下都保留。降级会直接打印出来：

```
上下文 782 / 800 tokens（已降级：文风压缩、伏笔→0 条、规则→1 条）
```

### 评审与改写（双轨）

硬校验负责"对不对"，Critic 负责"好不好"，两者不混：

1. 硬校验有 `error` → 直接 `rejected`，**不送 Critic**——不在错的东西上讨论文笔；
2. 无硬伤 → Critic 打分，并给出**具体到句子**的建议；
3. 低于阈值（默认 7.5）且有建议 → 带建议改写；
4. 改写稿必须**重新通过硬校验**才会被采用，否则保留原稿；
5. 改写后重新评审，记录的分数是最终稿的分数。

```
评审 7.0 / 10（按评审意见改写 1 轮）
  · 「手一松，碑身往前滑了半尺」与隔两句的「他没撒手」读起来自相矛盾。改成「右手一麻，握不住」……
  · 「第二块跟得没长眼睛」是全知视角的俏皮旁白，跟前文冷静的白描不一致；删掉它，改用身体动作。
```

**Critic 只出建议，不能判章节无效**——那是硬校验的职权。这是刻意的权限划分：LLM 会幻觉，不能让它决定稿子的生死。

开关：`NOVEL_REVIEW=0` 或 `novel write --no-review`。评审 + 改写会让单章耗时从 20s 涨到 60s 左右，调试时可以关掉。

### 版本历史是有界的

每次 `save` 都会往 `canon_history` 写一份**全量快照**。5 章时每版 10 KB 无所谓，但按 5.6 KB/章外推，500 章时单份 Canon 约 2.7 MB、版本约 700 个——**全量历史会到 GB 级**。

所以保留策略是有界的：**最近 30 版 + 每 50 版一个锚点 + 永远保留第 1 版**，其余在每次保存后自动删除。

```
清理前: 15 版 / 151.0 KB
清理后:  6 版 /  69.6 KB   （保留版本 1, 5, 10, 14, 15, 16）
```

500 章时历史从约 1 GB 降到 **几十 MB**。代价是更早的版本只能跳到锚点回滚，不能逐版退回——版本历史本来就是用来救"刚刚写坏了一批章纲"，不是考古。

> 修正：早期版本说"500 章约 50-60 MB"，那是用 5 章的小项目反推的，偏高了。实测 1000 章的 canon 只有 1.11 MB（约 1.1 KB/章），历史与库体积见下面的压测。

> 删掉的页会被 SQLite 复用，所以**文件不会立刻变小**，但不会再继续涨。想回收磁盘空间可以手动 `VACUUM`。

### 断点恢复

每次 LLM 调用的产物按 **prompt 指纹**（task + model + system + user）存进 SQLite。
进程中途被杀、超时、崩溃，重跑时已完成的调用直接复用，不重复烧 token。

```
$ novel write --ch 4        # 写到一半被 Ctrl-C
$ novel write --ch 4        # 重跑
第 4 章 · drafted  619 字
（复用上次中断留下的断点，未重复调用模型）
```

规则：
- 指纹包含 prompt 全文，**改了章纲或换了模型，旧缓存自动失效**，不会拿到过期内容；
- 空回复、以及 JSON 任务解析不了的回复，**不缓存**——缓存坏数据比不缓存更糟（真实踩过：坏 JSON 被缓存后，恢复时永远解析失败，而且失败被静默吞掉）；
- 只有整章成功落库才清断点；中途失败留下的断点下次能直接复用；
- `--fresh` 强制忽略断点重新生成。

### 成本统计

每次真实调用（架构/预演/章纲/正文/评审/摘要）都记进 `runs` 表，带任务、章节、token 和耗时。

```
$ novel cost                 # 按任务
任务      调用   输入    输出    耗时
writer      8  10,693  10,222  14.0s
critic      2   2,232   4,564  25.8s
planner     1   1,644   1,485   8.7s
compress    2   1,822     399   3.6s

$ novel cost --by chapter     # 按章
$ novel cost --price-in 1 --price-out 2   # 顺便按每百万 token 估算
```

只统计真实调用——断点命中的复用不计费，所以这些数字就是实际花出去的钱。

> 升级前的历史记录只含 writer，且没有耗时字段；`--by chapter` 会忽略它们。

**评审值不值这个钱？** 实测：一次评审约 1.1k 输入 / 1.5-2.3k 输出、13s；一章正文约 1.4k 输入 / 3.6k 输出、20-25s。也就是说评审大约是正文 40-60% 的成本，换来 3-5 条可执行的修改建议。值不值取决于你改稿的时间成本，但至少现在这笔账是看得见的。

### 批量推进

单章约 100 秒（含评审），1000 章要几十小时——一个人守着点不现实。

```bash
$ novel batch --from 3 --to 4
完成 2 章（第3-4章） · 1,525 字 · 3.5 分钟
第3-4章 全部完成
```

行为：
- 缺章纲自动补（一次补 5 章，太多会超出单次规划的上下文）；
- 逐章汇报字数/状态/评分；
- 某章失败默认**停下来**，加 `--keep-going` 跳过继续；
- 失败后重跑同一条命令即可从断点继续，不会重复烧 token。

严格串行：章节之间有因果，并行会互相污染 Canon。

实测吞吐约 **100 秒/章**（评审开启）。关掉评审约快一倍。建议每晚跑 20-30 章，早上看 `novel status` 和失败列表。

### 导出成册

```bash
$ novel export --format docx
已导出 E:\book\断碑.docx
  3 章 · 2,327 字 · 40.5 KB
```

| 格式 | 说明 |
|---|---|
| `docx` | 封面 + 目录域 + 分章标题，中文宋体；需 `pip install "novel-engine[export]"` |
| `epub` | EPUB 3，含 nav 与 ncx 双目录，纯标准库实现，无额外依赖 |
| `txt` / `md` | 纯文本，适合直接贴到平台后台 |

- 章节顺序以 Canon 章号为准，**真实章号会保留**（第 1、3、4 章不会被改成 1、2、3）；
- 计划中但未写的章节自动忽略；未通过校验的章节默认跳过，`--include-rejected` 可强制带上；
- docx 的目录是 Word 域，打开后右键「更新域」才生成页码——这是 Word 的机制，不是缺陷。

## 千章压测

`python bench/scale.py` 会合成一个 1000 章的项目（60 角色、40 弧、80 伏笔、500 预演事件），只测数据层与检索层，不调模型：

| 指标 | 1000 章时 |
|---|---|
| Canon JSON | 1.11 MB（≈ 1.1 KB/章） |
| 读取 | 14 ms |
| 保存（含历史裁剪） | 17 ms |
| 组装写作上下文 | 20 ms |
| 检索（全书扫描） | 16 ms |
| 连续 200 次保存后 | 34 版历史 / 27.4 MB，库 40 MB |

结论：**数据层在千章规模完全不是瓶颈**，读写都在几十毫秒。真正贵的是模型调用——1000 章大约 600 万输出 token、十几小时串行时间。

压测也暴露了一个真问题：**规划 prompt 有 5,221 tokens，而角色只有 60 个**——角色卡是全量塞进去的，会随书线性增长。现在改成只给最相关的 20 个详细卡片，其余只给名字（封顶 100 个），同规模下降到 **3,211 tokens**，且不再随角色总数增长。预演也拿到了"已完成弧"的一句话走向，跨 40 条弧时不至于失忆。
